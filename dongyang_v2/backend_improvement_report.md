# 백엔드 코드 분석 및 개선 제안 보고서

## 1. 개요

본 문서는 현재 프로젝트의 백엔드 코드 전체를 최적화, 보안, 확장성, 코드 품질 관점에서 분석하고 구체적인 개선 방안을 제안합니다. 현재 시스템은 RAG 챗봇의 핵심 기능을 잘 구현한 훌륭한 프로토타입이지만, 프로덕션 수준의 안정적이고 확장 가능한 서비스를 위해 몇 가지 구조적인 개선이 필요합니다.

**가장 시급하게 개선해야 할 사항:**

1.  **DB 커넥션 관리 방식 변경**: 요청마다 커넥션을 열고 닫는 현재 방식은 심각한 성능 병목을 유발하므로 커넥션 풀링 도입이 필수적입니다.
2.  **동기 함수의 비동기 처리**: `bcrypt`와 같은 CPU 집약적인 동기 함수를 별도 스레드에서 실행하여 메인 이벤트 루프의 블로킹을 방지해야 합니다.
3.  **서버 기반 데이터베이스로 전환**: 동시성 및 확장성 확보를 위해 SQLite에서 `MySQL` 또는 `PostgreSQL`로의 전환이 필요합니다.

## 2. 상세 분석 및 개선 제안

### 2.1. 성능 및 최적화

#### 가. DB 커넥션 관리 (`app/routers/auth.py`, `app/database.py`)

-   **문제점**: 모든 API 요청마다 `get_db_connection()`을 통해 새로운 DB 커넥션을 생성하고 `conn.close()`로 명시적으로 닫고 있습니다. 이는 매우 비효율적이며, 동시 요청이 많아질 경우 커넥션 생성/해제 오버헤드로 인해 시스템 전체 성능 저하의 주된 원인이 됩니다.
-   **개선 제안**:
    1.  **SQLAlchemy 도입**: `SQLAlchemy`와 같은 ORM을 도입하여 커넥션 풀링(Connection Pooling)을 자동화하고 관리하는 것을 강력히 권장합니다.
    2.  **FastAPI 의존성 주입 활용**: ORM을 사용하지 않더라도, FastAPI의 `Depends`를 사용하여 요청-응답 주기 동안 커넥션을 재사용하고, 애플리케이션 생명주기(`lifespan`)와 함께 커넥션 풀을 관리해야 합니다.

#### 나. 비밀번호 해싱의 동기적 실행 (`app/auth.py`)

-   **문제점**: `bcrypt`를 사용한 비밀번호 해싱 및 검증 함수(`hash_pw`, `check_pw`)는 CPU를 많이 사용하는 동기(blocking) 작업입니다. 비동기 프레임워크인 FastAPI의 메인 이벤트 루프에서 이를 직접 실행하면, 다른 모든 요청의 처리가 지연되어 심각한 성능 저하를 유발합니다.
-   **개선 제안**: FastAPI의 `run_in_threadpool`을 사용하여 CPU 집약적인 동기 함수를 별도의 스레드에서 실행해야 합니다. 이를 통해 메인 이벤트 루프의 블로킹을 방지하고 비동기 처리의 이점을 극대화할 수 있습니다.

    ```python
    # 개선 예시
    from fastapi.concurrency import run_in_threadpool

    # 로그인 시 비밀번호 검증
    is_password_correct = await run_in_threadpool(check_pw, form_data.password, user_in_db['password_hash'])

    # 회원가입 시 비밀번호 해싱
    hashed_password = await run_in_threadpool(hash_pw, user_data.password)
    ```

#### 다. RAG 시스템의 동기적 초기화 (`app/rag_core.py`)

-   **문제점**: RAG 시스템의 모든 컴포넌트(임베딩 모델, LLM 등)를 애플리케이션 시작 시 동기적으로 로드하고 있습니다. 임베딩 및 LLM 모델의 크기가 클 경우, 애플리케이션 시작 시간이 매우 길어져 배포 및 재시작 시 유연성이 떨어집니다.
-   **개선 제안**: FastAPI의 `lifespan` 컨텍스트 매니저 내에서 `run_in_threadpool`을 사용하거나, 별도의 초기화 함수를 비동기로 만들어 모델 로딩을 백그라운드에서 처리하는 것을 고려할 수 있습니다.

### 2.2. 보안

#### 가. JWT 비밀 키 관리 (`app/config.py`)

-   **문제점**: `.env` 파일 예시에 하드코딩된 기본 JWT 비밀 키(`"a_very_secret_key"`)가 포함되어 있습니다. 이는 개발자가 실수로 해당 키를 프로덕션 환경에서 그대로 사용할 위험을 내포합니다.
-   **개선 제안**:
    1.  `config.py`에서 `JWT_SECRET_KEY`가 기본값인지 확인하고, 기본값일 경우 경고를 출력하거나 에러를 발생시키는 로직을 추가합니다.
    2.  `.env.example` 파일에는 키 값을 비워두어 사용자가 직접 강력한 키를 생성하도록 명확히 유도해야 합니다.

#### 나. API 요청 속도 제한 (Rate Limiting) 부재

-   **문제점**: 현재 API 엔드포인트, 특히 로그인과 같이 반복적인 시도가 예상되는 곳에 요청 속도 제한이 구현되어 있지 않습니다. 이는 Brute-force 공격이나 서비스 거부(DoS) 공격에 매우 취약합니다.
-   **개선 제안**: `slowapi`와 같은 라이브러리를 도입하여 IP 주소 또는 사용자 계정별로 특정 시간 동안의 요청 횟수를 제한하는 미들웨어를 추가해야 합니다.

### 2.3. 확장성 및 유지보수

#### 가. 데이터베이스 선택의 한계 (SQLite)

-   **문제점**: 사용자 인증 및 관리에 단일 파일 기반의 SQLite를 사용하고 있습니다. SQLite는 동시 쓰기 성능에 명확한 한계가 있으며, 여러 웹 서버 인스턴스로 확장(Scale-out)하는 것이 사실상 불가능합니다. `README.md`에는 MySQL을 언급하지만, 실제 코드는 SQLite를 사용하고 있어 불일치가 존재합니다.
-   **개선 제안**: 프로덕션 환경을 고려한다면 초기 설계대로 `MySQL`이나 `PostgreSQL` 같은 강력한 서버 기반 RDBMS로의 전환이 필수적입니다. 이 과정에서 `SQLAlchemy` 같은 ORM을 도입하면 특정 데이터베이스에 대한 종속성을 줄이고, `asyncpg`(PostgreSQL)나 `aiomysql`(MySQL) 같은 비동기 드라이버와 함께 사용하여 비동기 환경의 성능 이점을 극대화할 수 있습니다.

#### 나. 설정 관리의 경직성 (`app/config.py`)

-   **문제점**: 새로운 LLM 공급자(예: Anthropic)가 추가될 때마다 `config.py`의 `__init__` 메서드에 `elif` 분기문을 계속 추가해야 하는 구조입니다. 이는 OCP(개방-폐쇄 원칙)에 위배되며 유지보수성을 저해합니다.
-   **개선 제안**: 공급자별 설정을 딕셔너리나 별도의 Pydantic 모델로 구조화하여, 새로운 공급자가 추가되더라도 코드 변경을 최소화할 수 있도록 리팩토링하는 것이 좋습니다.

---

### 2.4. 코드 품질 및 가독성

#### 가. 라우터와 비즈니스 로직의 미분리 (`app/routers/auth.py`)

-   **문제점**: API 라우터 핸들러 함수 내에 데이터베이스 쿼리와 같은 핵심 비즈니스 로직이 직접 포함되어 있습니다. 이는 코드의 재사용성을 저해하고, 단위 테스트 작성을 어렵게 만듭니다.
-   **개선 제안**: **서비스 레이어(Service Layer)** 또는 **리포지토리 패턴(Repository Pattern)**을 도입하여 데이터베이스 관련 로직을 분리해야 합니다.
    -   **리포지토리**: 데이터베이스 테이블에 대한 CRUD 작업을 담당.
    -   **서비스**: 리포지토리를 사용하여 비즈니스 로직을 수행.
    -   **라우터**: HTTP 요청을 받아 서비스 함수를 호출하고, DTO를 통해 응답을 반환.

#### 나. 일관성 없는 네이밍 (`app/schemas.py`)

-   **문제점**: `UserSignupRequest` 스키마에는 `dept`라는 필드명이 사용되었지만, 다른 모델에서는 `department`가 사용되어 일관성이 부족하고 혼란을 유발할 수 있습니다.
-   **개선 제안**: 프로젝트 전반에 걸쳐 필드명을 `department`로 통일하여 명확성과 일관성을 확보해야 합니다.

## 3. 사용자 피드백 기반 추가 개선 사항

### 3.1. 전반적인 시스템 응답 속도 저하

-   **현상**: 사용자가 챗봇 질문 시 답변을 받기까지의 대기 시간이 길게 느껴집니다.
-   **예상 원인**:
    1.  **LLM 응답 지연**: 외부 LLM API(OpenAI, Google) 호출 및 응답 대기 시간이 가장 큰 비중을 차지할 가능성이 높습니다.
    2.  **Retriever 성능**: `ChromaDB`에서 관련 문서를 검색하는 과정, 특히 `mmr` (Maximal Marginal Relevance) 검색 방식은 단순 유사도 검색보다 계산량이 많아 느릴 수 있습니다.
    3.  **동기 작업으로 인한 블로킹**: 앞서 `2.1`에서 지적한 DB 커넥션, 비밀번호 해싱 등의 동기 작업이 누적되어 전반적인 응답성을 저해합니다.
-   **개선 제안**:
    1.  **스트리밍 응답 (Streaming Response) 도입**: LLM이 생성하는 답변 토큰을 실시간으로 프론트엔드에 전송하여 사용자의 체감 대기 시간을 획기적으로 줄일 수 있습니다. FastAPI의 `StreamingResponse`를 사용하여 이를 구현할 수 있습니다.
    2.  **Retriever 최적화**:
        -   `search_type`을 `mmr`에서 `similarity`로 변경하여 검색 속도를 높이고, `k` 값을 조정하며 성능과 정확도의 균형점을 찾습니다.
        -   `scripts/ingest.py`에서 문서 청크(chunk) 크기와 중복(overlap) 값을 조절하여 검색 효율성을 개선합니다.
    3.  **비동기 처리 적용**: `2.1`에서 제안한 내용들을 우선적으로 적용하여 I/O 블로킹을 최소화합니다.

### 3.2. 의미적 검색(Semantic Search) 품질 저하

-   **현상**: "아플 때"와 같이 문서에 직접적으로 존재하지는 않지만 의미적으로 "병가"와 관련된 질문에 대해 관련 문서를 찾아내지 못합니다.
-   **예상 원인**:
    1.  **임베딩 모델의 한계**: 현재 사용 중인 `jhgan/ko-sroberta-multitask` 모델이 특정 도메인(학사 규정)의 미묘한 의미 차이를 완벽하게 포착하지 못할 수 있습니다.
    2.  **질문-문서 간의 불일치**: 사용자의 구어체 질문과 문서의 공식적인 문어체 표현 간의 간극이 존재합니다.
-   **개선 제안**:
    1.  **쿼리 확장 (Query Expansion)**: 사용자의 원본 질문을 LLM을 사용하여 다양한 형태로 변환하거나 동의어를 추가하여 검색하는 기법을 도입합니다. 예를 들어, "아플 때"라는 질문을 -> "질병으로 인한 결석", "병가 신청 방법", "공결 처리 규정" 등 여러 키워드로 확장하여 Retriever에 전달할 수 있습니다.
    2.  **HyDE (Hypothetical Document Embeddings)**: 사용자의 질문에 대해 LLM이 먼저 "가상의 이상적인 답변 문서"를 생성하고, 이 가상 문서를 임베딩하여 실제 문서를 검색하는 기법입니다. 질문 자체보다 더 많은 컨텍스트를 가진 가상 문서가 검색 성능을 높일 수 있습니다.
    3.  **임베딩 모델 파인튜닝 (Fine-tuning)**: 장기적으로 가장 확실한 방법입니다. 학교 규정과 관련된 질문-답변 쌍 데이터를 구축하여, 현재 임베딩 모델을 해당 도메인에 맞게 파인튜닝하면 의미 검색의 정확도를 크게 향상시킬 수 있습니다.
    4.  **하이브리드 검색 (Hybrid Search)**: 현재의 벡터 기반 의미 검색과 전통적인 키워드 기반 검색(예: BM25)을 결합합니다. 이를 통해 의미 검색이 놓치는 키워드를 보완하여 검색 결과의 재현율(Recall)을 높일 수 있습니다.
